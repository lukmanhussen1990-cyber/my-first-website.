# Luxury Base — using and placing it

The **Luxury Base Spawner** (`pas:luxury_base_spawner`) builds a furnished two-storey villa in white quartz and dark
oak (18 × 15 footprint, 13 high) in front of you, layer by layer, in about 7 seconds. This page covers how the item
is used and how the script decides where and how to build. The design of the house itself is in
[HOUSE.md](HOUSE.md). The contract is in [SPEC.md §6](SPEC.md).

Code: `addon/behavior_pack/scripts/house/`

| file | role |
|---|---|
| `index.js` | `initHouse()`: registers the item handler (`onUseOn`, `onUse`) with the shared dispatcher (`lib/items.js`) |
| `placement.js` | the build flow: pre-checks, reservations, the job runner with its tick budget, item consumption and refund, placement and fallback, progress, verification, all player messages |
| `checks.js` | block classification (replaceable vegetation, liquids, solid ground), the structure write mask, and the tick-spread site scan |
| `rotation.js` | orientation math (facing → rotation → origin) and the Rotate90 calibration probe |
| `blueprint_meta.js` | generated by `tools/house/blueprint.py` (do not edit): size, entrance, floor level, support ratio, build time |

## How to use it

1. Stand on reasonably flat open ground and **look in the direction the house should extend**.
2. Either tap the ground with the spawner (use it on a block), or use it in the air while looking at the ground up to
   **12 blocks** away.
3. The site is checked (a fraction of a second). If something is in the way you get a message saying what and where,
   and **the spawner is not used up**.
4. If the site is clear, one spawner is used (survival and adventure only; creative keeps it), you hear the build sound,
   sparkles appear, and the house rises layer by layer. The action bar shows the progress.
5. About 8 seconds later you get **"Luxury Base complete!"** and the completion sound. Walk straight ahead up the front
   steps and through the double door.

Only one build per player runs at a time. Using the spawner again while your base is being checked or built only shows
a "please wait" message. Holding the use button counts as one use (the shared item dispatcher debounces).

## What you get (rooms)

**Ground floor** (one step up from the terrain):
* **Foyer** with a double front door, chiseled-quartz floor and sea-lantern floor tiles.
* **Staircase**: two-wide dark oak stairs up to the first floor.
* **Living room**: L-shaped sofa, rug, coffee table, bookshelf media wall, reading chair, floor-to-ceiling glass.
* **Crafting room**: enchanting table with 16 bookshelves, crafting table, furnace, blast furnace, stonecutter,
  smithing table, loom, anvil, and a chest of enchanting supplies.
* **Kitchen and dining**: smoker, furnace, cauldron sink, barrel cabinets, dining table with four chairs.
* **Storage**: 4 chests with starter supplies, barrels.
* **Back hall** and a covered **terrace / loggia** with planters and the front steps.

**Upper floor**:
* **Hall / gallery** with a lounge and a skylight over the stairs.
* **Master bedroom**: two beds, nightstands, desk, wardrobe barrels, chest, own balcony door.
* **Guest bedroom**: one bed, nightstands, desk, wardrobe barrels, chest, own balcony door.
* **Balcony** across the whole front, reachable through four doors.

Every room is lit to block light 9 or more, so hostile mobs cannot spawn inside. Doors: 9 in total. Details, plans and
pictures: [HOUSE.md](HOUSE.md).

## Orientation and position

The house always **extends away from you**, in the direction you are facing (rounded to north, east, south or west
from your yaw). Its **front door faces back toward you**.

The clicked ground column becomes the **outer terrace row, in line with the right-hand door leaf**. Seen from where you
stand, walking straight ahead:

```
 you  ->  front steps  ->  [clicked column]  ->  entrance cell  ->  front door  ->  foyer ...  back wall
          (1 before)        (outer terrace)       (1 beyond)         (2 beyond)                 (13 beyond)
```

* Width: 9 cells to your left of the clicked column, 8 to your right (18 in total). Depth: from 1 cell before the
  clicked column to 13 cells beyond it (15 in total). Height: 13 blocks.
* The foundation (local y 0) sits **on top of** the clicked block, so the ground floor is one step above the terrain and
  the bottom step is level with your feet.
* Tapping a plant (grass, flower, snow layer, ...) uses the real ground under it (up to 3 blocks down).
* In canonical form (`blueprint_meta.js`) the entrance is on the south side. The script picks the rotation that turns
  canonical south to face you: facing north → no rotation, east → 1 clockwise quarter turn, south → 2, west → 3.
  Placement origin = the rotated box's minimum corner (StructureManager.place semantics).

### Rotation calibration

The script does not trust an assumed direction for `StructureRotation.Rotate90`. Before the first real placement of
each session it measures it:

1. After the site scan has verified the build box, it picks a 4×1×4 area of plain air one cell in from a corner of the
   box (at local height `HOUSE.probeCell.y` = 4 first).
2. It creates an in-memory structure `pas:rotation_probe` (2×1×2, `StructureSaveMode.Memory`) with a single
   `minecraft:glass` at local (1,0,0) and void elsewhere, and places it with `Rotate90` at that spot.
3. It reads the cells back (up to 3 ticks): marker at (+1,0,+1) → Rotate90 is **clockwise** viewed from above; at
   (0,0,0) → **counter-clockwise**.
4. It sets every cell of the 4×1×4 area back to air, checks that they are air, and deletes the probe structure.
5. The result is cached for the session.

If anything fails (area not empty, structure API error, no marker or an unexpected position) the build uses the
fallback "Rotate90 = clockwise viewed from above" and logs a warning. Failures are retried on the next build. After 3
failures the fallback is cached. The fallback `/structure load` uses the same calibrated rotation value.

## Placement rules

All of these are checked before anything changes in the world. The first problem found is reported.

1. **Height**: the whole box (and the ground row under it) must be inside the dimension's height range
   (overworld y −64 to 319).
2. **Nobody inside**: neither you nor another player may stand inside the box.
3. **No overlap** with the box of another build that is still being checked or built (any player).
4. **Every cell loaded**: any unreadable cell (unloaded chunk) blocks with "area not fully loaded".
5. **Clear space**: every cell the structure writes must be air or natural replaceable vegetation:
   `short_grass`, `tall_grass`, `fern`, `large_fern`, `deadbush`, all small flowers (`yellow_flower` = dandelion,
   `poppy`, `blue_orchid`, `allium`, `azure_bluet`, the four tulips, `oxeye_daisy`, `cornflower`,
   `lily_of_the_valley`, `torchflower`, `pink_petals`), tall flowers (`sunflower`, `lilac`, `rose_bush`, `peony`,
   `pitcher_plant`), `snow_layer`, `vine`, `glow_lichen`, cave/weeping/twisting vines, `hanging_roots`,
   `spore_blossom`, mushrooms, nether fungi, roots and sprouts, plus `light_block` (the Tactical Torchlight's invisible
   light) and `structure_void`. Names are the 1.21.0.26 names from `mojang-blocks.json` (a test resolves each one).
   Saplings, crops, sweet berry bushes, cobwebs, azaleas, carpets and everything else block the build.
6. **Structure-void cells are lenient**: the 192 void cells (top layer inside the roof parapet) keep whatever is in the
   world, so solid blocks there are allowed and kept. **Liquids are not allowed anywhere in the box**, void cells
   included (`water`, `flowing_water`, `lava`, `flowing_lava`, `bubble_column`, `seagrass`, `kelp`).
7. **Solid ground**: at least **80 %** (`HOUSE.supportRatio`) of the 270 footprint cells directly under the foundation
   must be solid: not air, liquid, replaceable vegetation, or a thin or passable block (torches, rails, buttons, plates,
   signs, banners, carpets, saplings, crops, ladders, cobwebs, fire, ...).

The scan reads 3,510 box cells and 270 ground cells (3,780 `getBlock` calls). It runs as a job that may make at most
**600 `getBlock` calls per game tick**, shared by all builds in progress, so a scan takes about 7 ticks (0.35 s) and
never causes a frame hitch on mobile. The structure's write mask is read once per session (1,000 structure cells per tick).

## Building

* One spawner is consumed when the build starts (not in creative). If the player no longer holds it, one is taken from
  the inventory. If there is none, nothing is built.
* `world.structureManager.place("pas:luxury_base", dimension, origin, { rotation, animationMode: Layers,
  animationSeconds: 7, includeEntities: false, waterlogged: false })`.
* If that throws, the fallback is
  `dimension.runCommand("structure load pas:luxury_base <x> <y> <z> <0_degrees|90_degrees|180_degrees|270_degrees> none layer_by_layer 7 false true")`.
  The parameter order (name, position, rotation, mirror, animationMode, animationSeconds, includeEntities,
  includeBlocks) is checked against the `structure` overloads in `mojang-commands.json` for 1.21.0.26 by a test.
* If both fail: an error message with the reason, the spawner is given back (or dropped at the site if the player has
  left), and the box is released.
* The box stays reserved until `buildSeconds + 1` seconds after the start. Then the script checks the key blocks (both
  halves of both front-door leaves and the foundation under the entrance) against the structure's own blocks and
  reports the result honestly.

## Messages

| situation | chat message (actionbar and sound as well when blocked) |
|---|---|
| used in the air, nothing within 12 blocks | `Aim at the ground (within 12 blocks).` |
| something in the way | `Can't build here: oak_log at 12 70 -4 is in the way. Clear a 18×15 area (13 high) or pick flatter ground.` |
| liquid in the box | `Can't build here: water at 12 64 -4. The base can't be built in or over water or lava.` |
| not enough solid ground | `Can't build here: not enough solid ground (73% of the footprint, need 80%). First gap: air at 3 63 -6. Pick flatter ground.` |
| unloaded chunk | `Can't build here: area not fully loaded (16 64 9). Move closer and try again.` |
| too high / too low | `Can't build here: the base is 13 blocks high and would reach above the build limit (y 319). Pick lower ground.` |
| you are in the box | `Can't build here: you are standing inside the build area. Step back and try again.` |
| another player in the box | `Can't build here: Alex is standing inside the build area.` |
| overlapping build | `Can't build here: another Luxury Base is being built in this area (near x y z). ...` |
| second use while checking / building | `Still checking the build area...` / `Your Luxury Base is still being built (5s left).` |
| started | `Building your Luxury Base... (7s)`. The actionbar then shows `Building Luxury Base... 43%` every second |
| finished | `Luxury Base complete!` plus `pas.base.done` |
| key block missing afterwards | `Luxury Base finished, but dark_oak_door is missing at x y z (found air). The build may have been interrupted.` |
| area unloaded afterwards | `Luxury Base finished, but the area is not loaded any more, so it could not be checked.` |
| both placement paths failed | `The Luxury Base could not be placed (<reason>). Your spawner was returned.` |

Blocked feedback also plays the vanilla `note.bass` sound to the player. Builds play `pas.base.build` and
`pas:build_sparkle` at the site.

## Tests

`npm test` runs these against the behavioural mock with the real `luxury_base.mcstructure`:

* `tests/house_placement.test.mjs`:
  * all four facings on a flat grass plane: door halves (type, `direction`, hinge, upper bit) in the expected
    cells, the entrance cell free, the steps (`weirdo_direction`), every block inside the expected box (which extends
    away from the player), all 2,001 non-air structure blocks placed, item consumed exactly once;
  * creative mode, and use in the air (raycast hit or "Aim at the ground");
  * blocked sites, each with an exact message, no block changed, item kept, no reservation left: a stone pillar,
    a small log build, water, water in a void cell, a cliff (73 %), an unloaded chunk (getBlock returning undefined
    or throwing), the height limit, the player or another player inside. Also accepted cases: exactly 80 % support,
    and a solid block in a void cell;
  * vegetation (short and tall grass, flowers, snow layer, light block, vine) replaced; clicking a plant uses the ground
    under it;
  * overlap between two players while the first base animates; one build per player; hold-to-use builds once;
  * `/structure load` fallback (exact command string, house still correct) and the double failure (refund, release);
  * completion check: a missing door, an engine that builds nothing, an unloaded area;
  * the per-tick `getBlock` budget, for one scan and for two scans at once.
* `tests/house_rotation.test.mjs`: the orientation math (bijection, inverse, agreement with the mock's clockwise
  transform, anchoring for all facings, command enum and overload order from `mojang-commands.json`) and the
  calibration against the mock configured **both ways** (`mock.setOptions({rotate90: "cw" | "ccw"})`): measured
  direction, probe cells restored to air, probe structure deleted, result cached (one probe for two builds), full east
  and west builds correct under both conventions, a control showing that a blind Rotate90 would put the door elsewhere
  on a counter-clockwise engine, and the failure paths (occupied probe area, `createEmpty` error, rotation ignored,
  off-by-one placement).

## Limitations and what cannot be verified offline

* **Not tested in the game.** No Bedrock client is available here. The behaviour is verified against the mock, the
  1.21.0.26 script metadata, `mojang-blocks.json` and `mojang-commands.json`.
* **The animation runs in the engine.** `animationMode: Layers` is carried out by the game. The script only waits
  `buildSeconds + 1` s and then checks a few key blocks. It does not watch each layer. If the area unloads mid-build
  (the player runs away), the engine queues or finishes the placement on its own. The result message then says the
  area could not be checked.
* **Reservations are in memory.** Saving and reloading the world while a base is being built forgets the reservation
  and the pending completion message (the engine's own placement is not affected).
* **Block entities use defaults** where the structure has no NBT: barrels, furnaces, smoker, blast furnace, cauldron and
  enchanting table get the game's default block entities when placed. Bed colours, chest contents and flower-pot plants
  come from the structure's `block_entity_data`. Whether the game accepts that NBT exactly as written (PocketMine 5.16
  layout plus wiki fields) cannot be checked offline.
* **Assumptions the probe cannot fully prove:** the calibration measures the direction of Rotate90 and assumes that a
  rotated structure keeps its minimum corner at the placement location (the documented `/structure load` behaviour).
  A single marker cannot tell every misplacement apart: a clockwise turn shifted by (−1, −1) looks exactly like a
  counter-clockwise one. Any other misplacement within one cell is rejected, and the marker is cleaned up.
* **Synchronous probe placement** is expected for loaded chunks. If the marker is not visible at once, the script
  re-reads for up to 3 ticks, then falls back.
* `Structure.setBlockPermutation` is listed in the 1.11.0 metadata but marked `@beta` in the npm typings. If the stable
  module did not expose it, the probe fails cleanly and the clockwise fallback is used.
* `/structure load` requires cheats when typed by a player. It is only the fallback path, and commands run from scripts
  normally do not need cheats. This was not tested in game.
* The write mask and the expected key blocks are read with `world.structureManager.get("pas:luxury_base")`. If the game
  did not return the pack structure there, the scan becomes strict (every box cell, void cells included, must be air or
  vegetation) and the completion check only requires the key cells to be non-air. Placement itself is unaffected.
* Mobs or items inside the box are not checked (only players). The structure is placed with `includeEntities: false`.
* Block-state rotation (doors, stairs, beds, trapdoors, barrels) is done by the engine. The mock follows PocketMine 5.16
  semantics, so the in-game result depends on the engine agreeing with those semantics (see HOUSE.md).
